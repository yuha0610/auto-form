# auto-form

お問い合わせフォームへの自動営業ツール。Googleスプレッドシートをマスターに、
対象企業のフォームを一括で開いて自動入力し、人が確認・送信した結果をスプレッドシートへ自動で記録する。

## 構成

- Googleスプレッドシート — 対象企業リスト・フォーム営業履歴・備考・商談状況のマスター
- `data/templates/*.json` — 営業文面テンプレート(会社名・氏名・連絡先・件名・本文)。`subject`/`message`内の`{{companyName}}`は送信時に対象企業名(空なら「貴社」)へ置換される
- `src/lib/targetSelection.ts` — スプレッドシートの内容から「今送るべき対象」を選ぶロジック
- `src/lib/formDiscovery.ts` — 企業のトップページからお問い合わせフォームのURLを自動探索
- `src/lib/formSubmitter.ts` — フォーム項目をラベル/name/placeholderのキーワードから推測して入力し、入力状況をバナー表示
- `src/lib/completionCheck.ts` — 送信後のページ状態から成功/要確認を判定
- `src/lib/sheetsClient.ts` — Google Sheets APIとの読み書き
- `src/index.ts` — CLIエントリーポイント(バッチ実行)

## セットアップ

```bash
npm install
npm run playwright:install
```

1. Google Cloudでサービスアカウントを作成し、Google Sheets APIを有効化する
2. 対象スプレッドシートをサービスアカウントのメールアドレスに編集者権限で共有する
3. サービスアカウントのJSONキーを `credentials/google-service-account.json` に置く
4. `.env.example` を `.env` にコピーし、`GOOGLE_SERVICE_ACCOUNT_KEY_PATH` と `GOOGLE_SHEET_ID` を設定する
5. スプレッドシートのヘッダー行に「フォームURL」列を追加する
6. スプレッドシートのヘッダー行に「メールアドレス」列を追加する(お問い合わせ先がメールアドレスのみの企業を記録する列。この列がないとツールが起動しない)
7. スプレッドシートのヘッダー行に「検知シグナル種別」「検知日」「検知元URL」の3列を追加する(資金調達・求人などのシグナル検知結果を記録する列。この3列がないとツールが起動しない)
8. (任意)Slackで「Incoming Webhooks」を有効化し、通知先チャンネルを選んでWebhook URLを発行、`.env` の `SLACK_WEBHOOK_URL` に設定する。設定しない場合はSlack通知がスキップされる

## 目標件数の管理(任意)

スプレッドシートに「進捗」という名前のシートを追加し、以下のセルに目標を書くと、
バッチ完了時のSlack通知に累計件数・残り営業日・必要ペースが追記される。

| セル | 内容 | 例 |
|---|---|---|
| B1 | 目標件数(数値) | 1000 |
| B2 | 期限(`YYYY/MM/DD`) | 2026/07/31 |

「進捗」シートが無い、またはB1・B2が空/不正な値の場合は、この追記はスキップされる
(「今日の送信件数」通知自体は今まで通り送られる)。

## コマンド早見表

日常の営業作業で使うのは上の2つだけ。それ以外はリストのメンテナンス用で、必要なときだけ使う。

| コマンド | 用途 | 危険度 |
| --- | --- | --- |
| `npm run dev` | フォーム営業のバッチを開く(自動入力あり) | 送信を伴う |
| `npm run retry:form-missing` | 備考が「フォーム無」の企業のHPを開く(自動入力なし) | 送信を伴う |
| `npm run match:signal-sweep` | 収集した資金調達イベントをリストと突き合わせる | 読み取りのみ |
| `npm run apply:signals` | 検知シグナルをシートに反映(行の追加あり) | `--apply` で書き込み |
| `npm run update:funding-info` | 資金調達情報をシートに反映 | `--apply` で書き込み |
| `npm run cleanup:company-names` | 企業名の表記を修正し、重複行を削除 | `--apply` で**行を削除** |
| `npm run screen:competitors` | 同業他社と判定した行を削除 | `--apply` で**行を削除** |
| `npm run screen:non-startup` | 非スタートアップと判定した行を削除 | `--apply` で**行を削除** |
| `npm run screen:starcla` | スタクラ掲載企業を「送信NG」にする | `--apply` で書き込み |
| `npm run mark:skip` | 貼ったURLの企業にスキップ印を付ける | `--apply` で書き込み |
| `npm run rescan:form-missing` | 「フォーム無」の企業を再スキャンして送信対象に戻す | `--apply` で書き込み |
| `npm run record` | バッチの結果をまとめてシートに記録する | `--apply` で書き込み |
| `npm run cleanup:notes` | 積み上がった備考を整理し、失敗続きの企業を打ち切る | `--apply` で書き込み |
| `npm run list:uncertain` | 送信できたか確認が取れていない行を一覧に書き出す | 読み取りのみ |

`--apply` を付けない限り、いずれのメンテナンススクリプトもシートを変更しない(内容の確認だけ)。
行を削除するスクリプトは取り消せないので、`--apply` を付ける前にシートのバックアップを取る。
また、行を削除すると以降の行番号がずれるため、他の書き込み作業と同時に走らせない。

## 使い方

```bash
# 既定20件のバッチを開く
npm run dev

# バッチサイズを指定する
npm run dev -- --batch-size 10
```

対象は「直近30日以内に資金調達などのシグナルがある企業」を検知日の新しい順に優先し、
それ以外はシートの並び順で選ばれる。

タブが開いたら、各タブを順番に確認し、キャプチャ対応・送信ボタンのクリックを人手で行う。
すべて終わったらターミナルでEnterキーを押すと、開いた企業の一覧が表示され、
送信できなかった企業のURLを貼るよう促される。貼られた企業は備考に「送信失敗」と記録され、
それ以外は送信結果を自動判定して記録する。URLはブラウザのアドレスバーからコピーすればよく、
どの企業のものかはツールが判定するので企業名を覚えておく必要はない。

URLを貼り終えると、続けて「送信できたか自動で判定できなかった企業」の一覧が出る。
ページに「ありがとうございました」等の完了文言が無く、URLも変わらなかった企業がここに並ぶ。
実際には送信できていない企業の番号を答えると、その企業には送信日を入れず「送信失敗」として記録する。
すべて送信できていればそのままEnterでよい。

この確認を挟まないと、送信していない回にも日付が入り、14日後に自動で次の回へ進んでしまう
(2回目を送っていないのに3回目に進む、という状態になる)。

確認中にCAPTCHA(「私はロボットではありません」等)が表示された企業は、送信を試さずタブを閉じれば、
ページ内のreCAPTCHA/hCaptcha/Turnstileを検知して備考に「CAPTCHA」と自動記録され、
次回以降のバッチで自動的にスキップされる。

営業を断る旨がサイトに明記されていた企業は、備考に「営業・セールスお断り」と手で記入しておくと、
次回以降のバッチで自動的にスキップされる。

理由を問わず今後送りたくない企業は、備考に「送信NG」と記入しておくと、
`npm run dev` でも `npm run retry:form-missing` でも二度と対象にならない
(「フォーム無」の再挑戦モードは他のスキップ理由を無視するが、「送信NG」だけは常に除外する)。

手でシートを開かなくても、URLを貼るだけで印を付けられる。

```bash
# 確認のみ(既定の印は「送信NG」)
npm run mark:skip -- https://example.com/contact https://another.example.jp/

# 確認した内容のまま書き込む
npm run mark:skip -- https://example.com/contact --apply

# 「送信NG」以外の印を付ける
npm run mark:skip -- https://example.com/contact --reason CAPTCHA --apply
```

URLはスペース・カンマ・改行のどれで区切ってもよく、会社URL・フォームURLのどちらでも同じ行に
突き合わせる(パスが違ってもホストが同じなら拾う)。`--reason` にはシートで実際にスキップとして
効く印しか指定できない。効かない印を書いてしまうと、外したつもりの企業に送信してしまうため。

同じホストの行が複数あってどの企業か絞れないURLは、取り違えを避けて書き込まず「要確認」として
一覧表示する。シートに見つからなかったURLも黙って捨てず一覧に出る。

## バッチの結果をまとめて記録する

ターミナルの案内に従わずに送信作業をした場合など、後からまとめて結果を記録したいときに使う。
1件ごとに「どのURLの企業が」「どうなったか」を書いたJSONファイルを渡す。

```bash
npm run record -- data/batch-result.json           # 確認のみ
npm run record -- data/batch-result.json --apply   # 反映
```

```json
[
  { "url": "https://example.com/", "outcome": "sent", "formUrl": "https://example.com/contact" },
  { "url": "https://other.example/", "outcome": "email", "email": "info@other.example" },
  { "url": "https://third.example/contact", "outcome": "failed" },
  { "url": "https://fourth.example/", "outcome": "skip", "reason": "リンク切れ" }
]
```

| outcome | 記録する内容 |
| --- | --- |
| `sent` | まだ日付の無い送信回に今日の日付を入れる(1→2→3回目の順) |
| `email` | 「メールアドレス」列に保存し、備考を「メール」にする |
| `failed` | 備考に「送信失敗」を追記する |
| `skip` | `reason` に指定したスキップ印を付ける |
| `form-url` | 「フォームURL」列だけを更新する |

`formUrl`は`sent`/`failed`/`form-url`で、`email`は`email`で、`reason`は`skip`で使う。
どの結果でも備考から「フォーム無」は外す(実態と合わなくなるため)。
すでに同じ印が付いている行や、人が手で入れたフォームURL・メールアドレスは上書きしない。
`sent`で3回とも送信済みの行は、書き込まずエラーとして一覧に出す。

`mark:skip`と同じく、URLが複数行に一致した場合と1行も一致しなかった場合は書き込まず一覧表示する。

バッチの送信結果をスプレッドシートに記録した後、その時点での「今日の累計送信件数」がSlackに通知される(`SLACK_WEBHOOK_URL` を設定している場合のみ)。

## 読み込みに失敗した企業の扱い

サイトを開けなかった企業は送信日が入らないため、そのままでは次のバッチでも対象に残る。
毎回同じ企業ばかり開かれるのを防ぐため、失敗の種類で打ち切り方を変えている。

| 失敗の種類 | 備考に付く印 | 扱い |
| --- | --- | --- |
| URL不正(名前解決失敗) | `URL不正(名前解決失敗)` | 開き直しても直らないので1回で打ち切る |
| 証明書エラー | `証明書エラー(URL要確認)` | 同上 |
| 原因不明の読み込み失敗 | `読み込み失敗(要確認)` | 同上 |
| タイムアウト | `タイムアウト(再試行済・要確認)` | 1回目は対象に残し、2回目で `接続不可` を付けて打ち切る |
| 接続エラー | `接続エラー(再試行済・要確認)` | 同上 |

打ち切られた企業を送信対象に戻したいときは、シートの備考からその印を消す。
URLが間違っているだけの場合は、会社URLを直してから印を消す。

同じ印が何度も積み上がってしまった古いデータは、次のコマンドで整理できる。

```bash
npm run cleanup:notes            # 確認のみ
npm run cleanup:notes -- --apply # 反映
```

同じ印は1つにまとめ、一時的な失敗を2回以上繰り返していた行には `接続不可` を付けて対象から外す。
手で書いた備考(日付を含むものも)は区切りと誤認せずそのまま残す。

## フォームが自動検出できなかった企業への対応

備考に「フォーム無」が付いた企業は、サイトは生きているのに問い合わせフォームのリンクを
自動発見できなかったケースが多い。このモードでは企業HPをそのまま開くだけで、
自動入力も自動送信も一切行わないため、誤送信の心配なく手作業でフォームを探せる。

```bash
npm run retry:form-missing -- --batch-size 5
```

その前に、まず再スキャンで自動的に戻せる企業を戻しておくとよい。
問い合わせ導線の検出は後から改善しているため、「フォーム無」が付いた時点では
見つけられなかった企業でも、今なら見つかることが多い。

```bash
# 確認のみ(結果は data/form-rescan-results.json に保存される)
npm run rescan:form-missing

# 確認した内容のまま反映する(再スキャンせずファイルから読む)
npm run rescan:form-missing -- --apply --from-file
```

フォームが見つかった企業は「フォームURL」列にURLが入り、備考から「フォーム無」が外れる。
これで次回の `npm run dev` から自動入力付きの送信対象に戻る。
問い合わせ先がメールアドレスだった企業は「メールアドレス」列に保存して備考を「メール」に、
Google Formだった企業は「Google Formで不可」に印を差し替える。
見つからなかった企業とサイトに到達できなかった企業は「フォーム無」のまま残す。

1社ずつ結果をファイルに書き出すので、途中で止めても次回は残りだけをスキャンする。
人が手で入れたフォームURL・メールアドレスは、再スキャンの結果で上書きしない。

送信できたら、そのページのURLをコピーしておく(タブはすぐ閉じてよい)。
すべて終わってEnterを押したあと、送信できた企業のURLをまとめて貼る。
貼られたURLはそのまま「フォームURL」列に保存されるので、次回以降は `npm run dev` の
自動入力対象になる。URLを貼らなかった企業には何も記録されず、次回also対象として残る。

外部のフォームサービスを使っていてドメインが一致しない場合は、どの企業のURLか番号で聞かれる。

## 注意事項

- フォーム構造はサイトごとに異なるため、フィールドの自動検出・送信結果の判定には限界がある。判定できない場合はバッチ終了時に人へ確認し、答えなかった企業は備考に「要確認」を付けて送信済みとして扱う。
- 過去に「要確認」のまま送信済みになった行は `npm run list:uncertain` で一覧を書き出して見直せる。
- 送信ボタンのクリックや「私はロボットではありません」等の対応は自動化せず、必ず人が行う。
- 送信先サイトの利用規約やスクレイピング/自動送信に関するポリシーを事前に確認すること。
- 過度な連続アクセスは相手サーバーに負荷をかけるため、バッチサイズや実行間隔に配慮すること。

## スプレッドシートの企業データクリーニング

企業名の表記ゆれ・不可視文字・重複行を整理するメンテナンススクリプト。

1. ドライラン実行してレポートを確認する:
   ```bash
   npm run cleanup:company-names
   ```
2. 出力の「要目視確認グループ」を確認し、それぞれ同一企業かどうかをFable 5などで判定する
3. 判定結果を `data/cleanup-decisions.json` に追記する(ファイルが無ければ新規作成):
   ```json
   [
     { "coreName": "luup", "merge": true },
     { "coreName": "arch", "merge": false, "notes": "別会社と判定" }
   ]
   ```
   `coreName` はドライラン出力の `[coreName]` 部分をそのまま使う。

   **注意:** `merge: true` を設定すると、同じコア名を共有する行が3つ以上ある場合、その全ての行が1つに統合される(判定した2社だけでなく、グループ全体が対象になる)。3行以上のグループで一部だけ同一企業と判定できる場合は、`merge: false` のままにして手動で個別対応すること。

   また、統合は主となる行(判定ロジックで残る行)以外を丸ごと削除する。破棄される行にしかない情報(例: その行だけに入力されたフォームURLや備考)は残す行にはマージされず失われるため、復旧はこのツールではなくGoogleスプレッドシート自体の変更履歴に頼ることになる。
4. 再度ドライラン実行して、想定通り統合対象グループに移っていることを確認する
5. 問題なければ実際に反映する:
   ```bash
   npm run cleanup:company-names -- --apply
   ```

商談確定日・フォーム営業1〜3回目の日付列は対象外。統合時は「商談確定日がある行 > 送信回数が多い行 > 元の行順で先頭」の行を残し、他方は行ごと削除する。

## 同業他社のスクリーニング

企業名・企業URLのトップページ内容から、人材紹介・RPO・営業代行(セールスBPO)など同業他社にあたる企業を検出し、除外するメンテナンススクリプト。

1. ドライラン実行して候補一覧を確認する:
   ```bash
   npm run screen:competitors
   ```
2. 出力された候補(企業名・URL・根拠)を目視確認する
3. 問題なければ実際に削除する:
   ```bash
   npm run screen:competitors -- --apply
   ```

キーワードでの機械的な判定のため誤検出・見逃しがあり得る。`--apply`前に必ず候補一覧を確認すること。

## スタクラ掲載企業のスクリーニング

スタクラ(`startupclass.co.jp`)に掲載されている企業は、すでに接点があるため
フォーム営業の対象から外したい。このスクリプトは求人一覧・企業一覧から掲載企業を取得し、
シートの行と突き合わせて備考に「送信NG」を追記する。行の削除は一切しない。

1. ドライラン実行して対象一覧を確認する:
   ```bash
   npm run screen:starcla -- --include-not-hiring
   ```
   求人一覧・企業一覧の全ページと、各企業ページ(会社URLの取得用)を0.7秒間隔で取得する
   (10分程度)。取得した掲載企業は `data/starcla-companies.json` に保存され、あとから
   「何を根拠に送信NGにしたか」を追える。ページの取得に3回失敗した時点で中断する
   (一部だけ取り落として、掲載中なのにNGが付かない企業が黙って残るのを防ぐため)。

   | オプション | 効果 |
   | --- | --- |
   | `--include-not-hiring` | 今は求人が出ていない掲載企業も対象にする(付けないと求人掲載中のみ) |
   | `--skip-urls` | 企業ページの取得を省いて社名だけで照合する(速いが取り逃しが増える) |
   | `--from-file` | 保存済みの `data/starcla-companies.json` を使い、取得をしない |
2. 出力された対象一覧(企業名・求人件数・送信履歴・商談状況・現在の備考)を目視確認する
3. 確認した内容のまま反映する:
   ```bash
   npm run screen:starcla -- --apply --from-file
   ```
   `--from-file` は保存済みの `data/starcla-companies.json` を使って再取得を省く。
   付けない場合は取得し直すため、ドライランで見た一覧と結果がずれることがある。

突き合わせは2通りで行う。ひとつは法人格の表記ゆれを吸収したコア名一致(`cleanup:company-names`と
同じロジック)。スタクラの社名欄には「Landit Inc. / ランディット株式会社」のような併記や、
キャッチコピー・旧社名が混ざって入っていることがあるため、それらを落とした別名でも照合する。
もうひとつは企業ページの「会社URL」とシートの企業URL/フォームURLのドメイン一致で、
社名の表記が全く違う企業もこちらで拾える。ただし複数企業が共有するホスト
(tally.so・studio.designなど)はドメイン一致の対象から除く。

社名は一致するのに双方のURLのホストが食い違う行は、同名の別会社(例: スタクラの
「株式会社WHERE」= `pntwhere.com` と、シートの「株式会社WHERE」= `where123.jp`)の
可能性があるため自動ではNGにせず、「要確認」として一覧の最後に出す。

同じコア名の行が複数ある場合はその全てが対象になるので、一覧の目視確認を省略しないこと。
商談状況が入っている行(すでに顧客になった企業)も対象に含まれ、一覧では `[商談中]` と表示される。

## 資金調達/求人シグナルの反映

Workflow等で調査した資金調達・求人掲載などの「検知シグナル」結果を、スプレッドシートに反映するメンテナンススクリプト。既存企業の「検知シグナル種別」「検知日」「検知元URL」列の更新と、シートに無い新規企業の行追加の両方を行う。事前に「セットアップ」の手順7でこの3列をヘッダー行に追加しておくこと。

### 期間で絞って集めた調達イベントから作る場合

Workflowで「直近N週間の資金調達」をまとめて収集した場合は、収集結果を
`data/signal-sweep-raw.json` に `{ "range": {...}, "events": [...] }` の形式で保存し、
以下を実行すると、企業名をシートの行と突き合わせて `data/signal-research-results.json` を生成する。

```bash
npm run match:signal-sweep
```

シートを読むだけで書き込みは行わない。企業名の突き合わせは表記ゆれを吸収するコア名で行い、
一致した行は既存シグナルの更新候補、一致しなかったものは新規発掘候補として振り分けられる。
発表日は `YYYY-MM-DD` で持たせておけば、シート形式の `YYYY/MM/DD` に変換される。

### 調査結果を直接用意する場合

調査結果は `data/signal-research-results.json` に、以下の形式で保存しておく:

```json
{
  "existingSignals": [
    { "rowIndex": 5, "companyName": "サンプル株式会社", "signalType": "資金調達", "signalDate": "2026/08/01", "sourceUrl": "https://prtimes.jp/...", "confidence": "high", "reason": "PR TIMESで確認" }
  ],
  "newCandidates": [
    { "companyName": "新規株式会社", "companyUrl": "https://newco.example.com/", "signalType": "求人", "signalDate": "2026/08/01", "sourceUrl": "https://example.com/jobs", "confidence": "high", "reason": "Wantedlyで新規掲載" }
  ]
}
```

1. ドライラン実行して反映内容を確認する:
   ```bash
   npm run apply:signals
   ```
   既存企業の更新候補・新規追加候補・それぞれの要確認項目(confidenceがlow、既存シートとの重複、競合/非スタートアップキーワード一致など)が出力される。新規追加候補のうち、企業ページの内容審査が未実施(URLが無い、または取得/解析に失敗した)の行には `(内容未審査)` が付く。
2. 出力内容(特に要確認項目・内容未審査の行)を目視確認する
3. 問題なければ実際に反映する:
   ```bash
   npm run apply:signals -- --apply
   ```
   書き込み直前にシートを再取得し、既存企業の更新は手動編集や行ズレが無いか、新規企業の追加は手動追加などで重複していないかを再確認したうえで反映する。再確認でスキップされた行はその場でログに出力される。

## 学習塾・セミナー系(非スタートアップ)のスクリーニング

企業名・企業URLのトップページ内容から、学習塾・予備校・家庭教師・セミナー事業など、スタートアップではない教育サービス系の企業を検出し、除外するメンテナンススクリプト。

1. ドライラン実行して候補一覧を確認する:
   ```bash
   npm run screen:non-startup
   ```
2. 出力された候補(企業名・URL・根拠)を目視確認する
3. 問題なければ実際に削除する:
   ```bash
   npm run screen:non-startup -- --apply
   ```

キーワードでの機械的な判定のため誤検出・見逃しがあり得る。`--apply`前に必ず候補一覧を確認すること。
